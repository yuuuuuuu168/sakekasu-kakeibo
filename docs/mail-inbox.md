# 下書き登録 API（Muse）

通販のメールから、家計簿にレシートの下書きを 1 件置く API。Muse（メールの分類と抽出を受け持つ外部の AI）と
取り決めた内容の正本で、Muse 側の仕様書（改訂版）とずれたらこちらに合わせて伝え直す。
実装は `infra/lambda/mail-inbox/`、鍵の発行と差し替えは [operations.md](operations.md) の「下書き登録の鍵（Muse）」にある。

## 流れ

1. 家計簿の中継（`infra/lambda/mail-relay/`）が 5 分ごとに Yahoo!メールを IMAP で見に行き、新着を全件 Muse Mail へコピーする
   （Yahoo! の自動転送は転送したメールを Yahoo! 側に残さないため。手順は [operations.md](operations.md) の「Yahoo!メールの中継（Muse）」）。
   設定画面の「メールの転送」で、差出人か件名のどちらかに当たるメールだけに絞れる（空なら全部を送る）
2. Muse が領収書のメールを選び、店名・品目・金額・注文番号を抜き出して利用者に知らせる
3. 利用者が「登録する」と答えたら、Muse がこの API を呼ぶ
4. 家計簿には **未紐付けのレシート**（`status: pending`、`source: mail`）として入る。明細はまだ作らない
5. カードの明細を取り込むと、いつものマッチ（金額と日付）でレシートと明細が結び付き、品目ごとに内訳が付く

通販はクレジットカード払いに固定する前提で組んである。メールから明細を直接作ると、後から取り込む
カードの明細と同じ支払いを二度数えるので、レシートとして置いてカードの明細を待つ。
画面で開くと支払い方法はクレジットカードから始まる（現金のまま登録すると二重に数える）。

## 中継したメールの形

送り主は `relay@kakeibo.sakekasu-builder.com`、件名は `Fwd: <元の件名>`。本文の頭に次の行を書き、その後に元の本文が続く。
添付は合計 10MB まで元のまま付け、超えたら外して、外したもののファイル名と大きさをこの欄に書く。

```
---------- 転送されたメッセージ ----------
差出人: "Amazon.co.jp" <auto-confirm@amazon.co.jp>
宛先: …@yahoo.co.jp
日付: 2026-11-22 13:05（日本時間）
件名: Amazon.co.jp ご注文の確認
Message-ID: <…@…>
```

## エンドポイント

`POST {ApiUrl}/draft-entries`。URL は API のスタックの出力 `MailInboxUrl`（HTTPS のみ）。
画面のドメインではなく API Gateway のドメインになる。

## 認証（Bearer トークン）

この経路だけ、画面のログイン（共通のユーザープールの JWT）を通らない。Muse はブラウザでログインできないため。
代わりに、この経路専用のトークンを送ってもらう。

```
Authorization: Bearer kkb_…
```

- トークンは `kkb_` で始まる 32 バイトの乱数。この経路でしか使えず、ほかの API の JWT の代わりにはならない
- サーバーにはトークンの SHA-256 だけを置く（Secrets Manager、読めるのはこの関数だけ）。シークレットを読まれても
  トークンは戻せない。トークンそのものは発行したときに 1 回だけ表示され、Muse の安全な入力フォームに入れる
- 鍵の期限は 90 日。失効は Secrets Manager の一覧から消すだけで、次の呼び出しから 401 になる。
  差し替えの間は新旧を並べておける
- 401 の本文はどれも同じで、どこで落ちたかは返さない。理由はログに残す（送られたトークンはログに出さない）

初めは HMAC-SHA256 の署名で取り決めたが、Muse の資格情報の仕組みに、秘密の値を持ったまま署名を作る経路が無かったので、
Bearer トークンに切り替えた（2026-11-22）。署名と違って、通信の途中で盗まれたトークンはそのまま使えて、送り直しも防げない。
通信は HTTPS だけで、トークンでできるのはレシートを 1 日 20 枚まで足すことだけ（読み出し・更新・削除はできない）、
送り直しは重複の判定で既存の下書きが返るだけになる、の 3 つで受け止めている。

## リクエスト

`Content-Type: application/json`。

| 項目 | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `date` | string | 必須 | 注文日。実在する `YYYY-MM-DD` |
| `store` | string | 必須 | 店名・モール名（200 文字まで） |
| `title` | string | 必須 | 商品名・内容の代表表記（200 文字まで） |
| `amount` | integer | 必須 | カードに請求される金額（ポイント・ギフト残高を引いた後）。1 以上 30,000 以下 |
| `order_number` | string / null | 必須 | 注文番号。無ければ `null`。画面と同じ規則でそろえる（全角・ダッシュの揺れ、数字の無いものは無しと同じ） |
| `source` | string | 必須 | `"mail"` 固定 |
| `message_id` | string | 必須 | 元のメールの Message-ID（500 文字まで）。中継したメール自身の Message-ID ではなく、本文の頭の `Message-ID:` の行（ヘッダの `X-Original-Message-ID` と同じ）の値 |
| `items` | array / null | 任意 | `{ "name": string, "amount": integer }` の配列。1〜50 行。送料・割引・ポイント利用も 1 行（割引は負の数）。合計は `amount` と一致させる |
| `category` | any | 任意 | 受け取っても使わない |

`items` が無ければ、`title` と `amount` を 1 品目にする。

カテゴリは Muse に決めさせない。画面で写真から読んだときと同じ順番で、覚えた品目のルール → 判定（Jev）→
キーワード表で当て、決まらない品目は未分類のまま置いて、利用者が画面で決める。

本文は 64KB まで。

## 応答

| 状態 | いつ | 本文 |
| --- | --- | --- |
| 201 | 新しく置いた（同じメールの登録し直しを含む） | `{ "id": "r-…", "status": "draft" }` |
| 200 | 既にあった（下の「重複」） | `{ "id": "<既存の id>", "status": "draft" }` |
| 401 | トークンが無い・一致しない（失効を含む）、期限切れ | `{ "error": "unauthorized", "message": "認証に失敗しました" }` |
| 422 | 本文の検査に通らない | `{ "error": "validation_error", "details": [{ "field", "message" }] }` |
| 429 | 1 日（日本時間）20 件を超えた、または短い間に続けて呼んだ | `{ "error": "rate_limited", … }` |

`id` は文字列で、中身に意味は無い。`status` は `"draft"` 固定。
1 日の件数は、認証の通った呼び出しを数える（200・422 も含む）。短い間の連続は API Gateway が絞る（毎秒 1 回、瞬間 3 回）。

## 重複

同じ注文で「注文確認」と「発送のお知らせ」が届くので、次のどれかに当たれば作らずに 200 で既存の `id` を返す。

- 同じ注文番号のレシートがある（画面で注文画面の写しから先に登録したものも含む）
- 同じ Message-ID から置いたレシートがある
- 同じ注文番号・Message-ID で前に置いた印が残っている（別のメールから置いた下書きを画面で消した後も含む）

印は `MAILINBOX#<sub>` のパーティションに、注文番号と Message-ID の SHA-256 を `sk` にして置き、
レシートと同じトランザクションで「無ければ書く」。2 通がほぼ同時に届いても 1 件になる。
人が消した注文を、後から届いた発送のお知らせで置き直さないため、印はレシートを消しても残す。

### 同じメールの登録し直し

**同じ Message-ID から置いた下書きを画面で消していれば**（行を消した、または `discarded`）、同じ `message_id` で
送り直すと 201 で新しい `id` の下書きを置く。タイトルや品目を直して置き直すため（2026-11-23）。
Muse は利用者が「登録する」と答えたときだけ呼ぶので、同じメールがもう一度来るのは人が置き直したいときと見なす。

- 印は新しい `id` に書き換える。書き換えは「消したレシートの `id` を指している印だけ」の条件つきなので、
  登録し直しがほぼ同時に 2 回来ても 1 件になる
- 下書きが残っていれば、これまでどおり 200 で同じ `id` を返す（通信の失敗による送り直し）
- 別のメール（発送のお知らせなど、Message-ID が違う）は、注文番号の印が残っている限り 200 で消した `id` を返す。
  消した注文はこちらからは置き直さない

下書きの内容を書き換える API は置かない。この鍵でできるのはレシートを足すことだけ、という取り決めを崩さないため。

## ログ

1 回の呼び出しにつき `[mail-inbox]` の 1 行（CloudWatch Logs、保持 1 か月）。結果（作成 / 既存 / 認証失敗 /
検証エラー / 上限超過 / 失敗）、状態、`id`、鍵の ID、店名、日付、金額、品目名と金額、注文番号、当てたカテゴリ。
トークンは出さない（鍵の名前だけを出す）。

## 制限と、知っておくこと

- 30,000 円を超える注文は 422。画面で直接登録する
- Amazon の分割発送のように、1 つの注文が複数回に分けて請求されると、1 枚のレシートと明細 1 件のマッチにならない。
  画面で手で結ぶか、分ける
- 鍵が漏れても、できるのはレシートを 1 日 20 枚まで足すことだけ。読み出し・更新・削除はできず、
  置かれたレシートはカードの明細に結び付くまで集計に入らない
