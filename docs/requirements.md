# 要件

sakekasu-kakeibo は、クレジットカードと PayPay の明細を取り込んで、カテゴリごとの上限と突き合わせ、
月末に叱ってくれる家計簿。手入力をなるべくしないことが最優先の設計方針。

配信先は `https://kakeibo.sakekasu-builder.com`。利用者は本人ひとり。

## 解きたい問題

支出の記録そのものは明細でほぼ足りる。困るのは「どこで払ったか」しか分からないこと。
コンビニで 1,200 円使ったとき、おにぎりとティッシュペーパーが混ざっていても明細の見た目は 1 行で、
そのまま食費に落ちる。この粒度では「何に散財しているか」が分からない。

そこでレシートの写真を主軸に置く。撮った写真から品目と単価を読み取り、金額と日付で明細行に自動で
突き合わせ、品目ごとにカテゴリを付ける。レシートを撮り忘れた分は店舗ルールによる推定と、
ワンタップの内訳分割で補う。

## 機能要件

### F1. 明細の取り込み

CSV と PDF を受け取る。ブラウザ内で解析し、確定したものだけをサーバへ送る。

- CSV は Shift_JIS と UTF-8 の両方を読む。国内のカード会社は Shift_JIS がまだ多い
- 列の並びはカード会社ごとに違うので、ヘッダから日付・金額・店舗名を自動で推定する。
  推定を外したら画面で列を指定し直せる。指定した対応はソースごとに保存し、次回から使う
- PDF はテキスト層から起こす。テキストを持たない（画像として出力された）PDF は読めないので、
  その場でそう伝えて CSV を促す
- 同じ明細を二重に取り込まない。日付・金額・店舗名・ソースから決まる ID を振り、重複は上書きする

### F2. 自動分類

店舗名からカテゴリを推定する。推定の根拠は 3 段階。

1. 利用者が作ったルール。「セブン-イレブン は 食費」のような文字列パターンとカテゴリの対応
2. 初期搭載のルール。国内でよく出る店舗名を一通り入れてある
3. どれにも当たらなければ未分類にして、画面で目立たせる

ルールは、明細一覧でカテゴリを直したときに「この店は今後もこれにする」で増やせる。
ここを手動でメンテさせない。使っているうちにルールが育つ形にする。

### F3. 曖昧な店舗の内訳化

コンビニ、ドラッグストア、スーパー、Amazon、ホームセンターのように、1 回の支払いに複数カテゴリが
混ざる店は、カテゴリを推定した上で「内訳が未確定」の印を付ける。この印が付いた明細は、
レシートを当てるか、内訳を分割するまで残り続ける。

内訳の確定手段は 2 つ。

- レシート写真。撮ると品目ごとに分かれる（F4）
- ワンタップ分割。1,200 円を 食費 800 円 と 日用品 400 円 に割る。端数は最後の行に寄せる

### F4. レシート OCR と明細マッチ

レシートを撮ると、Bedrock の Claude に渡して店舗名・日付・合計・品目（名前と金額）を抽出する。
sakekasu-builder の `infra/lambda/ocr-analyzer` と同じ作りで、プロンプトと出力スキーマだけ差し替える。

抽出したレシートは、取り込み済みの明細と自動で突き合わせる。突き合わせの条件は合計金額の一致を必須、
日付の近さ（カードは利用日と計上日がずれるので前後 4 日まで）と店舗名の近さでスコアを付ける。
候補が 1 件で高スコアなら自動で紐付け、そうでなければ候補を並べて選ばせる。

現金払いのレシートは対応する明細が無い。この場合はレシートそのものを支出として登録する。

### F5. カテゴリ管理

最初の数か月は試行錯誤するフェーズなので、カテゴリは後から動かせる前提で作る。

- 追加、改名、並べ替え、無効化
- 統合。「コンビニ」を「食費」に寄せると、過去の明細も全部付け替わる
- 分割の逆操作はしない。代わりに、明細一覧を店舗で絞ってまとめて付け替える

初期セットは 14 個入れてある（後述の design.md）。多すぎたら統合、足りなければ追加で調整する。

### F6. 上限と進捗

カテゴリごとに月の上限を設定する。月は跨いでコピーできる。

ダッシュボードに、当月の実績と上限、消化率、残り日数から見た着地見込みを出す。
上限の 8 割を超えたカテゴリは警告色にする。

### F7. 月末の叱りレポート

毎月 1 日に前月分のレポートを生成する。EventBridge から Lambda を叩いて事前に作っておき、
画面はそれを読むだけにする。

レポートの中身は、カテゴリ別の実績と上限の差、超過額の大きい順、前月との比較、そして叱り。
叱りは超過率で 5 段階に分ける。上限を守れていれば褒める。守れていなければ超過の大きいカテゴリを
名指しして叱る。文面は固定のテンプレートから組む。ここを LLM に任せると毎月言うことが変わって
比較できなくなるし、テストも書けない。

### F8. 定期的な支払い

サブスク、分割払い、奨学金のように金額と周期が分かっている支払いを、設定（歯車）から先に登録する。
名前、金額、カテゴリ、引き落とし日、初回の月、周期（毎月〜年 1 回）を持つ。終わりが決まっている
ものは回数か最終月を、総額が決まっているものは総額を任意で入れる。

登録したものは明細を生やさない。着地見込みと残り回数の材料としてだけ持つ。明細を作ると
取り込んだ明細と必ず重なり、そのたびに重複の判定を通すことになるため。口座引き落としのように
明細を取り込まない支払いは、見込みの中にだけ現れる。

- 着地見込みに、その月のまだ発生していない分を日割りとは別枠で足す。取り込み済みの分は
  日割りの対象から外してそのまま数え、二重に数えない
- 回数か総額を入れたものは、あと何回でいくら残っているかを設定とダッシュボードに出す
- 固定費もカテゴリの上限に含めて数える。別枠にすると上限の意味が二重になるため、
  代わりにダッシュボードで定期支払いの分を分けて見せる
- 金額が動くもの（電気代など）は目安として登録できる。明細が取り込まれたら実績の額で見込む
- 月末の叱りレポートには入れない。締めた月は実績が出そろっていて見込みが要らないうえ、
  節約しようのない固定費を叱っても行動が変わらないため
- 停止したものは消さずに残す。過去の月の見込みを再現できるようにするため

## 非機能要件

- 利用者は 1 人。サインアップは閉じる。Cognito のユーザーは手で 1 つ作る
- 明細は個人の金銭情報なので、S3 と DynamoDB は暗号化し、S3 は公開しない。
  レシート画像は署名付き URL 経由でのみ読み書きする
- レシート画像は 90 日で自動削除する。OCR で抽出した品目はデータとして残るので、画像は要らなくなる
- 費用は月 1 ドル以内を目標にする。Bedrock の OCR がほぼ全部で、レシート 100 枚で数十円
- 手で AWS コンソールを触る作業を残さない。DNS レコードの追加だけは例外（operations.md）

## やらないこと

- 銀行 API やカード会社へのスクレイピングによる自動連携。明細の手動アップロードで始める
- 収入や資産の管理。支出だけを見る
- 複数人での共有。世帯の概念を入れない。必要になったら作り直す
- レシートの画像そのものの長期保管。OCR 結果だけ残す
